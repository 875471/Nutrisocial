# 30. Integración continua del backend

## Objetivo y problema

Las pruebas del backend (161 en `backend/test/`) solo se ejecutaban a mano antes de cada commit. Nada impedía subir a `main` un cambio que las rompiera, y como Render despliega automáticamente desde `main`, ese cambio llegaría a producción sin que nadie lo notara. El objetivo es que cada push y cada pull request ejecuten las pruebas y marquen el commit como fallido si alguna no pasa.

## Decisiones técnicas

**GitHub Actions, porque el repositorio ya está en GitHub.** No hace falta otra cuenta ni otro servicio, y el plan gratuito basta de sobra para un proyecto de este tamaño.

**Solo pruebas, sin despliegue.** El pipeline no despliega: Render ya lo hace por su cuenta al recibir un push a `main`. Encadenar el despliegue a que las pruebas pasen exigiría desactivar el despliegue automático de Render y llamar a su *deploy hook* desde el workflow, con un secreto más que gestionar. Para el alcance del TFG basta con que un fallo sea visible (aviso en GitHub y badge en rojo).

**Sin base de datos en el pipeline.** Las pruebas sustituyen el cliente de Prisma por un doble en memoria, así que no necesitan PostgreSQL. Sí hace falta `npx prisma generate`, porque los módulos cargan `@prisma/client` al importarse. No se usa ningún secreto: las pruebas fijan su propio `JWT_SECRET` y claves falsas.

**Filtrado por rutas.** El workflow solo se lanza cuando cambia algo en `backend/` o el propio workflow; un cambio solo de la aplicación Android o de la memoria no lo dispara. También se puede lanzar a mano (`workflow_dispatch`).

## Cómo funciona

`.github/workflows/backend-tests.yml` define un único trabajo en `ubuntu-latest`: descarga el repositorio, instala Node 22 (la misma versión mayor que en local) con caché de npm, ejecuta `npm ci` sobre `backend/package-lock.json`, genera el cliente de Prisma y lanza `node --test "test/*.test.js"`. El runner nativo de Node devuelve un código de salida distinto de cero si alguna prueba falla, y con eso falla el trabajo. El `README.md` del repositorio muestra el badge de estado del workflow.

## Limitaciones

- No hay pruebas de la aplicación Android en el pipeline: necesitarían el SDK de Android y, las instrumentadas, un emulador, lo que alarga mucho cada ejecución.
- Que el pipeline falle no bloquea el despliegue en Render, solo lo hace visible. Para bloquearlo habría que proteger `main` con *branch protection* o desplegar desde el workflow.
- Las pruebas usan un doble de Prisma; un error que solo aparezca con PostgreSQL real (una migración que falta, un tipo distinto) no lo detecta el pipeline.
